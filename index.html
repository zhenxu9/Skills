Skill 创建教程 从零到一打造你的 AI 技能插件

最后更新：2026-07-24  |  面向读者：完全零基础的新手小白  |  参考来源：AI 大学堂《Skill 开发实战训练营》（讲师：胡劲松）

什么是 Skill？

简单来说，Skill（技能） 是给 AI 助手安装的 「专业培训手册」 — 它告诉 AI：当用户提出某种需求时，你该怎么思考、用哪些工具、遵循什么流程、注意哪些红线。

一个 Skill 本质上是一段 预设的系统级指令文本，当用户的对话匹配到某个 Skill 时，这段指令就会被注入到 AI 的上下文中，让 AI「切换」到该领域的专家模式。

更严谨的定义
Skill 是 AI Agent 生态中的可插拔扩展单元：每个 Skill 封装特定领域的专业指令与最佳实践，Agent 通过 use_skill 工具动态加载，从而从「通用助手」升级为「领域专家」。用户无需手动编写复杂指令，Agent 会自动匹配最优 Skill。

Skill 的核心价值

价值维度说明
专业化让通用 AI 变成领域专家。例如 invoice-retrieval Skill 让 AI 精准识别发票、提取结构化信息
流程标准化固化复杂任务的最佳实践。例如 file-organizer Skill 定义了「扫描→蓝图→确认→执行→撤销」五阶段安全流程
安全可控在 Skill 中写入安全红线、禁区规则，AI 必须遵守，避免越权操作
可复用一次编写，全平台共享。所有用户对话都能受益于同一份 Skill 指令

一个生动的类比

类比：餐厅的「岗前培训手册」
想象你是一家餐厅的老板，招了一位通用厨师。这位厨师会做菜，但不了解你的餐厅风格。

Skill 就是你给他的一本 岗前培训手册：
• name = 这本手册的标签（比如「日料专区」）
• description = 封面的简介（「日料制作全流程指导」）
• prompt = 手册正文（选材标准、刀工要求、调味比例、出餐顺序…）

当客人点了寿司，领班一看标签就把这本手册塞给厨师 — 厨师立刻按手册标准作业，出品稳定一致。

Skill 的「五元素」结构

在讯飞 Skill 平台的 SKILL.md 配置规范中，一个完整的 Skill 由 五个元素 构成。其中前两个是基础元数据，后三个是功能定义：

分类元素说明
基础元数据 NAME Skill 唯一标识符，建议 kebab-case 命名（如 hello-skill）
DESCRIPTION 功能描述（最长 1024 字符），是 Agent 判断是否加载该 Skill 的唯一依据
功能定义 TRIGGER 触发词 — 用户说什么话会激活本 Skill
ABILITIES 具体任务能力 — 本 Skill 能完成哪些事
OUTPUT 返回结果格式 — 输出长什么样、给下游如何消费
最小 SKILL.md 结构示例
name: hello-skill
description: 使用星火 Lite 模型生成一句 30 字以内的中文问候语

# 能力
abilities:
  - 根据用户场景生成个性化中文问候语
  - 支持多种问候风格（正式/轻松/温馨）
两种视角的对照
本教程前文把 Skill 拆成 name / description / prompt 三个核心字段，是从「指令注入」角度的简化模型；而五元素模型是从「平台配置」角度的完整规范。两者并不矛盾：prompt 内部就承载了 TRIGGER / ABILITIES / OUTPUT 的详细定义。

Skill 的能力边界

在动手之前，先想清楚：这个需求到底适不适合用 Skill 来做？ 学会「做减法」比堆砌功能更重要。下面用 5 类典型场景 + 5 类应避免场景帮你快速判断。

✅ 适合用 Skill 的 5 类场景

类别典型例子
内容生成PPT 生成、文章配图、小说写作
信息抽取会议纪要、简历解析、合同条款提取
数据处理表格整理、JSON 转换、批量改名
知识服务八股文刷题、面试陪练、英语口语
工作流编排日报生成、自动周报、跨工具调度
判断口诀
「有明确流程的领域任务」最适合 Skill：输入可预期、步骤可固化、输出可校验。

❌ 不适合用 Skill 的 5 类场景

类别原因 / 替代方案
强实时性（毫秒级）Skill 走 LLM 推理链路有延迟 → 直接 API + 前端
大规模并发单 Skill 实例难以扛量 → 异步队列 + 缓存
严格权限 / 合规需审计与隔离 → 企业内私有 Skill + RBAC
主观审美（品牌设计）AI 难判美感 → 人 + Skill 协同
需要真实世界操作Skill 无物理执行能力 → RPA + Skill

Skill 与 Tool 的互补关系

很多新手会混淆 Skill 和 Tool，其实它们是 Agent 生态中不同层级的能力：

维度Skill（技能）Tool（工具）
定位领域专家「培训手册」底层功能「接口」
粒度粗 — 封装一整套流程细 — 单一原子能力
例子file-organizerread_file / shell_executor
关系Skill 内部编排调用多个 Tool，Tool 是 Skill 的执行手脚
执行上下文与数据隔离
每个 Skill 在加载时拥有独立的执行上下文，Skill 之间通过中间产物路径（如临时 JSON 文件）传递数据，而非共享内存。这保证了跨 Skill 协作时互不污染、可回退。

优秀 Skill 的标准

什么样的 Skill 才算「优秀」？从设计原则、用户体验、执行效率三个维度，可以归纳出 五大评判标准：

标准说明
指令清晰度提示词必须明确、无歧义。AI 读不懂的模糊指令 = 不可控的行为
容错能力对异常情况和边界条件有优雅处理（「如果失败则…」「如果返回空则…」）
执行效率最小化不必要的工具调用和交互轮次，把最重要的规则放在最前面
用户体验输出格式友好、进度可见、错误提示易懂
可维护性结构化良好的 Skill 更易于迭代和调试（用 Markdown 标题分层）
一句话
好的 Skill = 清晰的触发条件 + 无歧义的指令正文 + 完善的兜底逻辑 + 友好的输出体验。

Skill 的核心组成

回到本教程的核心模型，一个 Skill 由 三个核心字段 构成，缺一不可：

字段含义作用
name Skill 的唯一标识符 系统内部路由的「代号」，AI 通过 use_skill(skill_name="xxx") 来加载
description Skill 功能的简短说明 决定 何时激活 该 Skill — 系统根据用户意图匹配描述文本，命中则注入 prompt
prompt Skill 的完整指令正文 注入 AI 上下文的「培训手册」，定义该领域下的工作流程、工具使用、安全规则等

name — 名称

规则：使用小写字母 + 连字符，如 invoice-retrieval、file-organizer。全平台唯一，相当于身份证号。

注意
name 一旦注册后不建议随意更改，因为系统内部的路由、日志、调度都以 name 为索引。改名等于换个新 Skill。

description — 描述

规则：用 1~2 句话清晰描述：什么时候用这个 Skill、它能干什么。系统会根据这段文字和用户输入做语义匹配。

编写公式
「当用户需要 [做什么] 时激活此技能 + 它能 [解决什么问题] + 不适用于 [排除场景]」
description 是触发的唯一依据
description 是 Agent 判断是否加载该 Skill 的唯一依据。写得不好，Skill 再好也不会被调用；写得好，即便功能简单也能精准触发。

硬性约束：最长 1024 字符，且必须包含三要素 — 触发词 + Use when + 第三人称。

prompt — 指令正文

规则：这是 Skill 的灵魂。prompt 就是一段详细的自然语言指令，告诉 AI：

  • 你是谁（角色定位）— 你是发票专家 / 文件整理师 / 图片处理大师？
  • 你要遵守什么规则 — 工具使用优先级、安全红线、禁止行为
  • 你的工作流程是什么 — 第一步做什么、第二步做什么、遇到异常怎么办
  • 你有哪些可用工具 — 哪些工具必须用、哪些工具禁止用

Skill 的注册方式

重要提示
Skill 不能 在对话中直接创建。它必须由 平台管理员 在后台管理系统中完成配置与注册。

注册流程概述：

  1. 进入后台管理
    管理员登录平台后台管理系统，进入「Skill 管理」模块。
  2. 填写基础信息
    输入 Skill 的 name（唯一标识符）和 description（激活条件描述）。
  3. 编写 Prompt 正文
    在 Prompt 编辑器中撰写完整的 Skill 指令。建议先在文本编辑器中打好草稿，反复推敲后粘贴提交。
  4. 配置触发规则（可选）
    设置触发条件：是否需要用户显式调用（use_skill）、是否支持自动路由匹配等。
  5. 提交审核 & 发布
    提交后由平台审核人员验证逻辑无误、安全合规，审核通过后全平台生效。

作为 Skill 开发者，你的核心工作就是设计并编写高质量的 prompt 文本，然后提交给管理员注册。

完整示范：一个 Hello World Skill

下面是一个最简单的 Skill 配置样例 — 当用户说「打个招呼」时，AI 会用多国语言问候：

"name": "hello-world",
"description": "当用户想要打招呼或问候时激活此技能。支持多国语言问候语生成。",
"prompt": "你是一个友好的多语言问候助手。
当用户与你打招呼时，请：
1. 先用用户使用的语言热情回应
2. 然后用 中文、英语、日语、法语、西班牙语 五种语言各说一句"你好"
3. 最后询问用户今天需要什么帮助

示例输出格式：
---

嘿，你好呀！ 👋

让我用五种语言向你问好：
- 中文：你好！
- 英语：Hello!
- 日语：こんにちは！
- 法语：Bonjour！
- 西班牙语：¡Hola！

今天有什么我可以帮你的吗？ 😊

---

注意：始终保持友好、积极的语气。"

逐行讲解

行 / 字段讲解
name: "hello-world" 全小写 + 连字符，简洁明了。如果用 "helloWorld" 或 "Hello_World" 就不规范。
description 明确写了 触发条件（"当用户想要打招呼"）和 能力范围（"多国语言问候"）。系统路由就靠这段文字判断是否激活。
prompt 第 1 行 角色定义："你是一个友好的多语言问候助手" — 让 AI 清楚当前身份。
prompt 步骤 1-3 工作流定义：用数字序号列出步骤，清晰、可执行、不遗漏。
prompt 示例 Few-shot 示例：直接给出期望的输出格式，AI 会严格模仿。
prompt 最后一行的「注意」 约束条件：补充语气要求，防止 AI 跑偏。

JSON 格式完整示例：

{
  "name": "hello-world",
  "description": "当用户想要打招呼或问候时激活此技能。支持多国语言问候语生成。",

}

进阶：来自实战训练营的 hello-skill 模板

下面是讯飞训练营给出的「复制即用」模板，它更贴近真实平台配置（含模型与触发词）：

name: hello-skill
description: 使用星火 Lite 模型生成一句 30 字以内的中文问候语。

# 步骤1: 接收触发
# 步骤2: 调用 LLM（星火 Lite）
model: spark-lite
prompt: 生成一句 30 字以内的中文问候语，语气温馨自然
# 步骤3: 解析结果
# 步骤4: 输出问候语
触发词设计示例
在 description / trigger 中明确列出中英文触发词，可大幅提升命中率：
中文英文
你好hello
嗨 / 嗨喽hi
打个招呼hey
你好呀 / 哈喽 / 大家好其他问候变体

进阶挑战（扩展练习）

  • 加随机 emoji：问候语后随机添加相关 emoji，增加趣味性
  • 时间段问候：根据上午 / 下午 / 晚上自动调整问候内容和语气
  • 可配置问候：允许用户自定义问候风格偏好（正式 / 轻松 / 温馨）

最佳实践与常见错误

命名规范

维度✅ 正确❌ 错误
格式file-organizerFileOrganizer、file_organizer
长度2~4 个单词this-is-a-very-long-skill-name-that-no-one-will-remember
语义描述功能，如 image-search无意义代号，如 skill-001
唯一性全平台唯一与已有 Skill 重名

Description 编写技巧

Description 直接决定 Skill 能否被正确激活
系统用 NLP 语义匹配来判断用户的意图是否命中某个 Skill 的 description。写不好 description，Skill 要么从不触发，要么在不该触发时乱触发。

编写公式（再强调）：

当用户需要 [具体操作/场景] 时激活此技能 + [核心能力一句话] + 不适用于 [排除场景]

对比示例：

❌ 差✅ 好
「处理发票的」 「当用户任务涉及发票的查找、识别、解析、信息提取时，必须激活本技能。适用场景包括：按时间段找出所有发票、批量提取发票信息、发票信息汇总成 Excel 表格等。」
太简短、太模糊，系统无法准确匹配 场景具体、触发词丰富、有明确的排除条件

description 三大常见反例

类型问题修改建议
太宽范围过大，不相关场景也触发精准限定使用场景，加「不适用于…」
太窄覆盖面不足，该触发时没触发合理扩展边界，补充同义触发词
太抽象模糊不清，无法匹配使用具体动词和场景，避免「处理」「管理」等泛词

Prompt 编写技巧

1. 结构化分层

用 Markdown 标题（#、##、###）将 prompt 分成清晰的层次：

  • ## 角色定位 — 定义 AI 的身份
  • ## 核心规则 — 写死必须遵守的铁律
  • ## 工作流程 — 用步骤列表描述 SOP
  • ## 禁止行为 — 用 ❌ 列出绝对不能做的事
  • ## 输出格式 — 给出期望的输出模板

2. 工具路由表

如果 Skill 依赖特定工具，用表格明确路由规则：

| 场景 | 使用工具 | 备注 |
|------|---------|------|
| 读取 PDF | read_file | 不使用 read_text |
| 编辑 Excel | excel-processing-and-analysis skill | 先 use_skill 加载 |
| 文件搬运 | file-organizer skill | 严禁直接用 shell_executor |

3. Few-shot 示例

在 prompt 中给出 1~2 个完整的「用户输入 → AI 应该如何响应」示例，AI 会以此为模板行动。

4. 安全红线

涉及文件删除、系统修改等敏感操作，必须在 prompt 中用醒目的 🔴 高风险 标记并写明确认流程。

常见踩坑点

坑现象解决方案
Description 过于宽泛 Skill 在不相关场景也被激活，干扰正常对话 加「不适用于...」排除条件，缩小匹配范围
Prompt 过于简略 AI 行为不一致，同一种请求得到不同结果 细化每一步操作，给出具体示例，去掉模糊表述
Prompt 过于冗长 Token 消耗过大，AI 可能忽略靠后的指令 删除不必要的解释性文字，用表格代替大段描述，把最重要的规则放在最前面
工具名写错 AI 调用了不存在的工具，任务失败 严格对照工具列表，确保每个工具名拼写无误
缺少兜底逻辑 遇到异常情况 AI 不知所措 在 prompt 中加入「如果失败则...」「如果工具返回空则...」等兜底分支
没有设置优先级 多个 Skill 同时命中时行为混乱 在 prompt 中明确「本 Skill 覆盖以下场景，其他场景交由通用 AI 处理」

实战案例拆解

下面拆解训练营中 4 个真实案例，分别对应前文「适合 Skill 的 5 类场景」中的不同类别，帮助你建立「需求 → Skill 设计」的直觉。

案例一：智能会议纪要生成器 信息抽取类

需求：把一段冗长的会议录音转写文本，自动提炼成结构化纪要。

SKILL.md 结构拆解

这是一个经典的信息抽取 + 工具编排型 Skill，SKILL.md 分为六大模块：

模块内容设计意图
头部 metaname: meeting-minutes；description 含触发词（会议录音、会议纪要、transcribe meeting）确保 AI 能自动识别用户意图并路由到此 Skill
输入声明明确文件类型（mp4/mkv/webm/m4a/mp3/wav/flac）、可选输出目录、可选日报生成降低用户沟通成本，AI 一看就知道要什么参数
执行步骤环境检查（ffmpeg + whisper）→ 提取音频（ffmpeg 转 WAV）→ 转录（whisper 模型）→ 修正幻觉 → 生成纪要 → 可选生成日报六步流水线，每步有明确的 Shell 命令和参数。
输出规范纪要 Markdown 文件（会议主题/参会人/讨论要点/决议/待办清单）；
日报仅保留工作视角（项目现状/需求/讨论结论/待跟进）		用表格约束输出字段，避免 AI 自由发挥导致字段缺失。
异常处理同一目录多录音文件合并生成日报、文件名不用空格用下划线规定细节边界的兜底逻辑。

设计亮点

  1. 六步流水线编排：环境检查 → 提取音频 → Whisper 转录 → 幻觉修正 → 生成纪要 → 日报，每步产出明确，步骤之间通过文件系统传递数据。
  2. Whisper 幻觉处理：Skill 明确标注了 Whisper 模型在静默段落会反复出现固定短语的已知问题，并规定修正策略，体现了对工具限制的深度理解。
  3. 日报与纪要分离：纪要保持完整信息密度（含产品介绍），日报精简为工作视角（只保留决策路径、项目现状、待跟进），展示了"同一输入 → 两个输出"的实用模式。

SKILL.md 结构拆解

这是四个案例中最复杂的一个，SKILL.md 长达 1110 行，内部实现了一个完整的长篇 / 网文创作操作系统。架构分为四层：

层级模块核心设计
入口路由首轮决策树（8 种入口）新建小说 / 续写 / 快写 / 修改 / 自动写完整本 / 完稿导出 / 质量检查 / 短故事模式。通过触发词（"写一本""继续写""快写""导出 epub"）自动分流，首轮必须给出可用产物而非空泛追问。
三阶段工作流策划期 → 连载期 → 收尾期每个阶段有明确的出口条件。阶段切换需通过检查点确认（人工模式）或自动通过（自动驾驶模式）。
写作循环10 步标准循环读取上下文 → 检查悬念 → 角色沙盘 → 导演裁决 → 场景拆分 → 写正文 → 质量检查（红绿灯）→ 回写状态。每章都是一个可验证的事务。
支撑系统角色沙盘 / 悬念管理 / 质量检查 / 角色模拟 / EPUB 导出 / 翻译角色沙盘让关键角色以有限信息"自己思考行动倾向"，导演再按优先级裁决（人物一致性 > 主线 > 悬念 > 大纲 > 爽点）——把"角色驱动力"写进了 prompt 约束。

设计亮点

  1. 自动驾驶模式：支持"自动写完整本"的全自动流程，含红灯重试上限（最多 2 次）、连续失败熔断（3 章不通过强制暂停）、每 5 章进度简报。这是 Skill 复杂度的顶峰——把质量护栏写进了自主循环。
  2. 角色沙盘模式：每个角色拥有独立运行时记忆文件（已知事实、误判、压力、关系判断）、角色可"反抗大纲"（自然倾向与原计划冲突时，导演必须裁决）、信息不对称（角色只知自己知道的，看不到未来剧情）。这是把「人物驱动」从口号变成了可执行协议。
  3. 红绿灯质量体系：红灯 4 项（变化原则、字数、钩子、人物一致）必须通过；黄灯 2 项（AI 味、对白）建议优化；绿灯 3 项（伏笔、节奏、人物弧线）收尾期统一检查。分级检查避免在初稿阶段过度打磨。
  4. 短故事旁路：长篇是默认入口，但"短故事模式"是完全独立的流程——6000 字最低标准、必须写入命名 Markdown 文件、对话只回报路径和字数。展示了"同一 Skill 内按模式分叉"的设计范式。
  5. 中断恢复协议：长期中断后返回时自动生成续写简报（当前进度 + 各线状态 + 人物位置 + 下章任务），自动驾驶直接继续，人工模式先确认。这是"持续性长任务"产品化的关键一环。

SKILL.md 结构拆解

实际 Skill 名为 baoyu-diagram，功能远超"文章配图"——它是一个通用 SVG 图表生成器，支持 9 种图表类型：

图表类型适用场景核心特征

Mind Map（思维导图）头脑风暴、主题探索中心节点、辐射分支、有机布局
Timeline（时间线）时间事件横向/纵向轴线、事件标记、时期跨度
Illustrative（概念图）概念解释、对比说明自由布局、图标、标注、视觉隐喻
State Machine（状态机）状态转换、生命周期圆角状态节点、标签转换、起止标记
Data Flow（数据流）数据变换管道处理气泡、数据存储、外部实体

设计亮点

  1. 完整设计系统：SKILL.md 内置了一套完整的 SVG 设计语言——8 色语义调色板（Primary/Secondary/Tertiary/Accent/Alert/Connector/Neutral/Highlight）、JetBrains Mono 字体系统（5 级字号）、网格背景、箭头标记库。AI 生成图表时直接引用，保证视觉一致性。
  2. SVG 绘制层级规范：规定严格的 8 层绘制顺序（背景 → 区域边界 → 连接线 → 遮罩层 → 组件框 → 文本 → 图例 → 标题），每层有对应的 SVG 代码模板。特别是"遮罩层"技巧——在组件框下放一个 opaque 矩形，防止半透明组件透过连接线——这种工程细节极少出现在 Skill prompt 中。
  3. 组件模式库：预定义了标准盒子、决策菱形、数据库柱体、区域边界、安全组等 5 种 SVG 组件模板，AI 直接套用而非每次重新设计。相当于 prompt 内置了 UI 组件库。
  4. 间距规则强制：组件最小间距（40px 垂直/30px 水平）、箭头标签留白 10px、区域边界内边距 20px、图例距底部 20px——把布局约束写成了工程规范，避免 AI 产出重叠混乱的图表。
  5. 输出管线：SVG 输出后自动调用 scripts/main.ts 生成 @2x PNG，一条命令完成矢量 + 位图双输出。

  4. 扩展层解耦：修仙引擎和世界观引擎放在 extensions/ 目录下，与核心 Skill 的面试功能隔离。这意味着可以独立迭代游戏系统，不影响核心题库和出题逻辑。

总结与建议

SKILL.md 已成为行业主流
Anthropic 于 2025 年 12 月将 Agent Skills 开源为跨平台标准。目前腾讯 CodeBuddy、字节扣子、火山引擎豆包、Dify 等均已跟进支持，SKILL.md 格式正在成为 AI Agent 技能的事实标准。

几条核心结论：

  • SKILL.md 生态最广：Anthropic / CodeBuddy / Coze / 豆包 / Dify 均兼容，一次编写、多平台迁移的成本最低。建议新手优先学习 Anthropic SKILL.md 规范。
  • 独立路线：百度千帆（ai-plugin.json + OpenAPI）和 OpenAI GPTs（GUI 配置）走的是各自独立的技术栈，与 SKILL.md 生态不互通。
  • 讯飞独立体系：本教程前文介绍的讯飞五元素结构（NAME / DESCRIPTION / TRIGGER / ABILITIES / OUTPUT）属于独立格式，仅在讯飞 SkillHub 生态中使用。好消息是核心设计思路（元数据 + 触发词 + 能力描述 + 输出模板）与 SKILL.md 高度一致，概念迁移成本低。
  • 五元素与 SKILL.md 并不冲突：讯飞训练营的五元素框架本质上是对 SKILL.md prompt 正文的写作方法论，NAME / DESCRIPTION 对应 YAML 字段，TRIGGER / ABILITIES / OUTPUT 对应正文章节，因此与 SKILL.md 生态并不冲突。
Marvis 对 SKILL.md 的支持
Marvis 内部也支持导入 SKILL.md 格式的 Skill，规范与 Anthropic 兼容。但需注意：不是所有 Skill 都可以导入——只有通过平台审核的 Skill 才能使用，用户无法在对话中自行导入外部 Skill 文件。

Loomy 四问向导详解

Loomy 的「使用 Loomy 创建技能」是一个 AI 引导的结构化四问流程，每一项都有实例提示，极大降低非开发者的参与门槛：

步骤引导问题实例提示
问题 1 这个技能应该让 Loomy 能够做什么？ 自动生成周报、处理特定格式文件
问题 2 什么时候应该触发这个技能？ 用户提到"帮我写周报"、上传 .csv 文件时
问题 3 预期的输出格式是什么？ 生成 Word 文档、输出代码、发送邮件
问题 4 是否需要设置测试用例来验证技能效果？ 可选，适合有明确可验证输出的场景

四问向导的设计巧妙之处在于：它恰好覆盖了本教程五元素框架中的 ABILITIES（问题 1）、TRIGGER（问题 2）、OUTPUT（问题 3），以及额外的质量保证环节（问题 4），NAME 和 DESCRIPTION 则由 AI 自动生成。即使用户完全不懂 Skill 技术细节，也能在 30 秒内完成一套完整的 Skill 定义。

Skill 互通性说明

两者都遵循 Anthropic SKILL.md 标准，底层均兼容 OpenClaw 生态，互通路径清晰：

  • SKILL.md 是通用语言：name + description YAML 字段两边都认，同一份 SKILL.md 可在两个平台间无缝迁移
  • SkillHub 是共享桥梁：基于 ClawHub CLI 协议，一次发布到 SkillHub，OpenClaw / Loomy / WorkBuddy 都能拉取
  • 目录结构一致：SKILL.md + scripts/ + references/ + assets/，两边完全对齐
  • 唯一不互通：平台独有扩展字段（如 WorkBuddy 的 allowed-tools）在 Loomy 上会被忽略，但不影响基础功能

进阶技巧

如何在 Prompt 中引用工具

Prompt 中可以明确指定 必须使用 或 禁止使用 的工具：

## 工具约束

### 必须使用的工具
- 读取发票图片 → 必须使用 `invoice_parsing` 工具
- 文件内容搜索 → 必须使用 `search_file`（query 模式）

### 禁止使用的工具
- ❌ 严禁使用 `shell_executor` 删除任何文件
- ❌ 严禁使用 `python_executor` 直接读写发票文件
注意
你引用的工具名必须与系统中实际注册的工具名完全一致。建议在编写 prompt 前先确认可用工具清单。

设置触发条件

Skill 的触发方式有两种：

触发方式说明适用场景
自动路由匹配 系统根据 description 自动判断用户意图是否匹配 常见场景的 Skill，如发票处理、文件整理
显式调用 AI 判断需要加载时主动调用 use_skill("skill-name") 需要精确控制的复杂流程 Skill

可以在 prompt 中写清楚触发策略，例如：

## 激活策略
本 Skill 支持自动路由匹配，当用户意图与以下场景匹配时自动激活：
- 用户提到"发票"、"报销"、"票据"
- 用户要求"找发票"、"整理发票"、"发票汇总"

多 Skill 协作

复杂任务往往需要多个 Skill 配合完成。比如「找出所有发票并生成汇总报告」这个任务：

  1. invoice-retrieval Skill — 搜索、识别、解析发票
  2. excel-processing-and-analysis Skill — 将解析结果写入 Excel
  3. document-writer Skill — 生成格式化的汇总报告

协作要点：

  • 每个 Skill 的 prompt 中写明 输出格式，方便下游 Skill 直接消费
  • 使用 中间产物路径（如临时 JSON 文件）在 Skill 之间传递数据，利用独立的执行上下文实现数据隔离
  • 在 prompt 的「禁止行为」中注明 本 Skill 不负责的部分，避免越界
  • 理解 跨 Skill 协作的模式与限制：Skill 之间不共享内存，只能通过约定格式的文件 / 消息传递
设计建议
单一职责原则：一个 Skill 只做一件事，做精做透。不要把发票识别、表格生成、报告撰写塞进同一个 Skill — 拆分成多个独立 Skill 更灵活、更易维护。

总结

创建 Skill 的本质是：把领域知识固化为 AI 可执行的指令模板。

记住这五步：

  1. 明确场景 — 这个 Skill 要解决什么问题？谁会用？它适合用 Skill 做吗？（参考能力边界）
  2. 设计名称 — 起一个简洁、语义清晰的 name
  3. 写好描述 — 用「触发条件 + 核心能力 + 排除场景」公式写 description（≤1024 字符，含触发词 + Use when + 第三人称）
  4. 编写指令 — 结构化撰写 prompt：角色→规则→流程→工具→示例→禁止项
  5. 测试发布 — 用真实场景验证触发与兜底，提交审核后发布上线
一句话总结
好的 Skill = 清晰的触发条件（description）+ 无歧义的指令正文（prompt）+ 完善的兜底逻辑 + 友好的输出体验。
